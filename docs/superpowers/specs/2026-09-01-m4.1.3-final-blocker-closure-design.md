# M4.1.3 Final Blocker Closure

## Scope

Close only five audited blockers: warning hygiene, selective incremental mutation,
one semantic pipeline, runtime data flow, and in-flight MCP cancellation with
meaningful benchmarks. No M5 work or new analyzer framework.

## 1. Warning hygiene

Remove every production and benchmark `allow(dead_code)`, `allow(unused)`, and
broad warning suppression. Retain an allow only when an external boundary or a
proven false positive requires it; it must be item-level, lint-specific, and
documented with a `LINT:` comment. The final gate is repository suppression
search plus warning-free `cargo check` and Clippy.

## 2. Incremental graph semantics

`IncrementalWorkspace` owns parsed files and per-file graph ownership. Ordinary
add, modify, and delete actions remove only stale file-owned nodes and extracted
edges, insert only the changed file state, compute semantic identity changes,
and re-resolve the affected closure. It must not call `build_graph` over every
cached file for a normal one-file edit.

Affected resolution covers the changed file plus direct importers, references
to changed definitions, type/inheritance/implementation dependents, re-export
consumers, and unresolved references newly satisfiable by an addition. Rename
may use a broader reconciliation only when module identity cannot be mapped;
the reason and counter are exposed in update statistics.

An authoritative clean repository build remains the oracle. Tests compare its
canonical graph with every incremental mutation and assert unrelated modules
were untouched.

## 3. Unified semantic pipeline

One internal finalization sequence owns semantic resolution, derived edges,
validation, and canonicalization. Clean build uses it after scan/parse;
incremental mutation invokes its affected-resolution portion; daemon and MCP
enter through the same storage/incremental engine. No path may publish a graph
with different resolution or canonicalization behavior.

## 4. Runtime value-flow graph

Existing AST-aware `LocalFlowGraph` becomes input to `DataFlowGraph`. It emits
parameter, binding, assignment, call-argument, callee-parameter, return, and
call-result relationships with source locations and confidence. Interprocedural
links are added only for resolved calls, or bounded possible candidates.

`graphia path` keeps structural traversal. `graphia flow` traverses only value
relations; Contains, Imports, and a call without transferred values cannot form
a flow path. Runtime language support reports only proven AST-aware coverage.

## 5. MCP cancellation and benchmark methodology

MCP stdio separates reader, bounded request workers, cancellation registry,
response channel, and one stdout writer. A cancellation notification can reach
the token while its request is running. Capacity and queue are bounded; tokens
are removed on every terminal request outcome.

Benchmarks call the same `IncrementalWorkspace` action used at runtime and
report update selectivity. Each RSS stage runs in a new child process, returning
a measured peak or explicit unavailable reason. No zero substitute.

## Verification

Targeted tests cover selective edits, clean equivalence, value-flow positives
and negatives, actual MCP stdio cancellation, bounded concurrency, and isolated
RSS smoke behavior. Final gate runs formatting, check, Clippy with warnings as
errors, and all targets/tests. Documentation records evidence, limitations, and
supersession of earlier M4.1.2 PASS claims.

## Boundaries

No full SSA, unlimited worker model, broad fallback for ordinary edits, or
unrelated refactor. Existing structures are extended only where they connect to
the actual runtime path.
