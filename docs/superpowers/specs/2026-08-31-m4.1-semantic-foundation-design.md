# Graphia M4.1 Workstream 1: Semantic Foundation and Schema Integrity

## Status

Approved on 2026-08-31.

## Context and decision

Graphia M0-M4 contains useful implementation, but current identity includes physical source location, normalized models are narrower than documented parser capabilities, and parser IR primarily carries symbols, imports, and calls. These contracts affect storage, incremental state, daemon snapshots, MCP, diffing, and benchmarks.

M4.1 will use five ordered workstreams:

1. semantic foundation and schema integrity;
2. incremental workspace core;
3. daemon and MCP reliability;
4. advanced-analysis correctness;
5. benchmark and documentation closure.

This design covers workstream 1 only. It establishes one compact semantic contract before runtime behavior changes. Later workstreams must consume these contracts rather than create competing identity, metadata, or confidence models.

## Alternatives rejected

### Three larger workstreams

Lower planning overhead, but schema failures become harder to isolate and runtime consumers can drift while identity remains unstable.

### One monolithic M4.1 change

Matches prompt structure, but creates a large cross-cutting diff and encourages partial capability claims when one subsystem blocks another.

Five gated workstreams are preferred because correctness and auditability outrank delivery speed.

## Scope

Included:

- separate semantic identity from physical source location;
- stable IDs for named symbols across line shifts and body-only edits;
- overload-safe identity through canonical signatures or semantic disambiguators;
- expanded normalized node, edge, visibility, signature, container, and confidence models;
- compact normalized parser IR;
- semantic coverage audit for all 16 advertised languages;
- real scopes only where parser facts support them;
- resolution for imports, exports/re-exports, type references, inheritance, implementations, instantiations, and calls;
- native-index and parsed-cache schema review and version bumps;
- explicit rejection of incompatible persisted artifacts;
- `docs/m4.1-closure-audit.md` and `docs/language-support.md`;
- removal of `missing_docs = "allow"` without replacement broad suppression.

Excluded:

- incremental graph mutation and affected-closure implementation;
- daemon, persistence-worker, and OS-signal redesign;
- MCP freshness, limits, and cancellation redesign;
- advanced-analysis correctness changes;
- RSS, Graphify comparison, and large benchmark implementation;
- compiler-grade typing, persistent Tree-sitter trees, unsupported block scopes, and M5 work.

Downstream modules receive only compile-preserving adaptation. Their behavioral gaps remain open in closure audit until later workstreams.

## Semantic identity

`SemanticNodeKey` determines identity. `PhysicalSourceLocation` records navigation metadata and does not participate in identity for named constructs.

Conceptual key:

```text
language
normalized module/file identity
symbol kind
qualified semantic name
container semantic identity
canonical signature or semantic disambiguator
```

Existing deterministic hashing may remain if it hashes this canonical key and retains collision validation.

Required behavior:

```text
insert blank lines                      => same NodeId
change function body only               => same NodeId
move named symbol in same container     => same NodeId
rename symbol                           => different NodeId
change identity-bearing signature       => different NodeId
same name with different overloads      => distinct NodeIds
```

Moving a symbol between normalized modules/files changes semantic ownership and therefore identity. Later graph diff must distinguish this from line-only location movement.

Anonymous/local constructs use the strongest deterministic structural key available: named container, kind, semantic role, and stable sibling discriminator. Line/column is last fallback only; such identity must be represented as location-sensitive, not silently stable.

## Normalized model

Required node kinds:

```text
File, Package, Module, Namespace,
Function, Method, Constructor,
Class, Struct, Interface, Trait, Enum,
Variable, Constant, Field, Property, TypeAlias
```

Parsers emit only source-supported kinds. Rust/Java/C enums map to `Enum`; constructors to `Constructor`; Go packages to `Package`; namespaces to `Namespace`; TypeScript aliases to `TypeAlias`.

Required edge kinds:

```text
Contains, Imports, Exports, Calls, References,
TypeReferences, Instantiates, Inherits, Implements
```

No edge kind is added without a parser, resolver, query, or analysis consumer.

Definitions carry, where known: visibility, compact canonical signature, container identity, physical location, language, and normalized source identity. Visibility is `Public`, `Protected`, `Private`, `Internal`, `Package`, or `Unknown`; unknown is never promoted to public. Signatures distinguish overloads and structural API changes without claiming compiler type fidelity.

Relation confidence becomes:

```text
Extracted: explicit syntax fact
Resolved: deterministic scope/import/type link
Inferred: heuristic relation with evidence
Possible: one of multiple plausible candidates
```

Unresolved references remain unresolved. Ambiguous references preserve bounded candidates as `Possible`; iteration order never chooses a winner.

## Compact parser IR

`ParsedFile` becomes equivalent to:

```rust
struct ParsedFile {
    definitions: Vec<Definition>,
    references: Vec<Reference>,
    imports: Vec<Import>,
    exports: Vec<Export>,
    calls: Vec<Call>,
    type_references: Vec<TypeReference>,
}
```

Names may follow repository conventions. Definitions include kind, name, qualified name, container, visibility, signature, and location. References include source scope/container, target spelling, semantic role, and location, not fabricated final IDs. Tree-sitter trees remain temporary; caches store normalized facts, not CST/AST nodes.

## Scope and resolution

Minimum real hierarchy:

```text
Project
Package, Module, or Namespace
File
Type
Function, Method, or Constructor
```

Scopes exist only for emitted facts. Block scope remains deferred unless local definitions and lexical ownership are extracted.

One candidate architecture resolves imports, exports/re-exports, types, inheritance, implementations, instantiations, and calls. Candidate evidence may include lexical scope, explicit imports, container, receiver type, signature/arity, inheritance, and implementation facts. Candidates and machine output are canonically sorted.

## Language coverage

Each advertised language receives evidence-backed status for definitions, methods, constructors, enums, interfaces/traits, package/module/namespace, imports, exports, calls, type references, inheritance, implementations, visibility, and signatures.

Allowed statuses: `FULL`, `PARTIAL`, `EXPERIMENTAL`, `UNSUPPORTED`. `FULL` requires implementation and fixture evidence for every applicable capability, not grammar parse success.

C/C++ header detection uses deterministic repository context: nearby translation units and extension relationships, then cheap C++ syntax signals, then documented C fallback. Scanner or hash-map order must not affect it.

## Storage compatibility

Identity inputs, enum variants, confidence meaning, and serialized IR trigger explicit schema review.

- bump native `index.bin` schema for identity/model changes;
- bump parsed-cache schema when payload or meaning changes;
- reject older, newer, corrupt, or incompatible artifacts with actionable errors;
- never reinterpret old IDs under new semantics;
- do not add ambiguous compatibility shims;
- do not silently fall back to `graph.json`.

Migration is allowed only when simple and semantics-preserving. Otherwise users rebuild explicitly.

## Error handling and determinism

- Unsupported syntax yields partial/unknown facts, not fabricated relations.
- Ambiguity remains visible.
- Invalid schemas fail before graph use.
- Canonical sorting removes persistent/public dependency on `HashMap` order.
- Production malformed state returns structured errors; test-only `unwrap`/`expect` may remain.
- Broad lint suppression is forbidden. Any narrow exception needs a `LINT:` technical rationale.

## Audit deliverables

`docs/m4.1-closure-audit.md` uses:

```text
Area | Claim | Actual implementation | Gap | Severity | Required action | Status
```

Severity is `P0 correctness`, `P1 important`, `P2 improvement`, or `DEFERRED`. Runtime and advanced-analysis findings remain open after this workstream.

`docs/language-support.md` records evidence and limitations per language. Existing reports receive full reconciliation in workstream 5; directly false semantic guidance may be marked pending earlier.

## Verification

Focused regressions:

- line shift and body-only edit preserve ID;
- rename changes ID;
- overload signatures produce unique IDs;
- enum differs from struct;
- constructor, namespace/package, visibility, signature, export, and type-reference extraction;
- re-export, type reference, overload, receiver typing, ambiguity, and unresolved resolution;
- old index rejection reports expected and actual version;
- incompatible cache is not reused;
- repeated builds produce canonical-equivalent graph and serialization.

Development uses targeted tests and affected checks. Workstream boundary runs formatting, affected tests/checks, and Clippy with `-D warnings`. Full all-target/all-feature validation remains final M4.1 closure gate.

## Acceptance criteria

Workstream 1 completes only when:

1. named semantic IDs exclude line and column;
2. overload identity is collision-safe and tested;
3. required node, edge, metadata, and confidence semantics exist;
4. compact IR supplies every relation accepted by resolver;
5. scope/resolution preserve unresolved and ambiguous outcomes;
6. all 16 languages have truthful status and evidence;
7. incompatible native index/cache schemas fail explicitly;
8. output is deterministic and canonical;
9. closure audit contains no false `PASS`;
10. compiler and Clippy warnings are zero without broad suppression.

## Follow-on dependency gates

Workstream 2 may begin only after identity, schema, canonical graph equivalence, and cache invalidation contracts pass. Workstream 3 depends on workstream 2's publish/persistence API. Workstream 4 depends on semantic metadata and confidence. Workstream 5 runs only after all prior behavioral gates and records measured, reproducible final status.
